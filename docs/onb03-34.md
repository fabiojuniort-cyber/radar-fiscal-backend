# ONB-03.4 — revisão explícita do perfil efetivo

Correção dos reviews 5669547613 / 5669548017. Escopo R2, tribusca-control#117. Sem migrations, backfill, merge, deploy ou escrita em produção.

GET onboarding acrescenta effectiveProfiles, projeção somente leitura de TODAS as escolhas canônicas, NCMs, regime, mapeamentos CNAE/segmento e campos livres históricos. Os valores globais anteriores são apresentados na matriz; uma filial nova não recebe esses valores. As escolhas anteriores permanecem armazenadas como estavam. historicalConcepts permite exibir o nome de conceitos de releases anteriores; um código sem nome conhecido continua visível pelo código, sem inventar rótulo.

concepts[].ncmCodes contém exclusivamente os códigos oficiais NCM do próprio produto na release publicada, normalizados sem pontos e sem completar zeros. Vínculos CNAE→produto e CNAE→NCM são independentes e não criam produto→NCM. Intervalos ou strings compostas não são convertidos em uma NCM inventada.

PUT selectionMode=EFFECTIVE é opt-in do novo web. Em segmento, units contém a fotografia efetiva completa de cada unidade participante, obrigatoriamente o conjunto exato de unidades ativas daquele segmento. Cada fotografia foi lida junto com expectedVersion. Lock da empresa, comparação de versão, tenant/RLS, OWNER/ADMIN, shared lock de publicação e releaseId permanecem obrigatórios. A confirmação substitui explicitamente o conjunto efetivo das unidades envolvidas; as outras unidades ficam intactas. O estado de retomada é sincronizado para não ressuscitar escolhas removidas de cards anteriores. Pular exige fotografia idêntica ao persistido; rascunhos novos não viram confirmação nem apagam escolhas antigas.

cardId=profile permite revisão completa de uma única unidade, inclusive sem CNAE/sugestões. Campos livres anteriores só podem ser mantidos/removidos, não se tornam novas tags livres. A matriz atualiza de modo coerente suas escolhas globais e o override; filiais não alteram a matriz. Origem de release de outras unidades é preservada quando a matriz adota uma release nova. Uma escolha histórica desconhecida precisa ser removida/substituída explicitamente antes de adotar a release corrente; a guarda não foi removida. Cards cadastrais não relabelam escolhas históricas, permitindo chegar ao resumo/editor. Conclusão recusa códigos históricos pendentes. Cada alteração cria nova versão; linhas históricas não são reescritas, salvo encerramento temporal normal de is_current/valid_to.

Contrato anterior de PUT/cards permanece disponível para navegadores anteriores. Implantação futura: backend antes de web. Web novo depende dos campos efetivos: não inverter a ordem. A proteção de versão permanece ativa. JavaScript anterior à introdução do guard ainda exige recarga manual; o backend nunca aceita versão ausente.

Testes: unidade para evidência produto/NCM, projeção global/unidade e filial vazia, sincronização sem ressuscitar escolhas; integração HTTP/PG16 para legado pré-carregado, GET sem escrita, correção explícita, preservação do histórico, limites de unidade, OCC e conclusão. Ciclo operacional PG18 continua cobrindo publicação/onboarding/reversão sem alteração de perfis. Nenhum desses testes escreve em produção.
